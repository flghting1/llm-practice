# SQL 数据分析 Agent 面试讲解

## 60 秒项目介绍

我做的是一个面向销售、客户和订单分析场景的受控 SQL 查询应用。用户输入自然语言问题后，系统把问题转换成 SQL，查询 SQLite，并通过 FastAPI 和 Streamlit 返回 SQL、结果解释、表格和图表。

项目的重点不是把模型权限放开，而是让查询可控。我在 SQL 执行层只允许单条 SELECT，拦截增删改和系统操作；再通过 SQLite Authorizer 限制可访问的表和字段。即使上层生成了不安全 SQL，数据库执行阶段也会拒绝。

如果 SQL 因常见字段名错误失败，系统最多进行一次确定性修复；第二次仍失败就停止，避免循环重试。我还建立了固定评测，覆盖正常查询、危险 SQL、无效问题和失败识别。当前自然语言转 SQL 使用规则实现，范围有限但结果可解释、可复现，下一步才是用真实模型替换上层生成模块，同时保留安全执行层。

## 面试讲解结构

按“业务痛点 -> 系统边界 -> 关键设计 -> 评测结果 -> 当前限制”讲，不从技术名词开始堆砌。

| 部分 | 要讲的内容 |
| --- | --- |
| 业务痛点 | 业务人员需要数据，但不应直接获得数据库写权限，也不一定会 SQL。 |
| 系统边界 | 当前只做只读分析，不执行写操作，不访问系统表和未授权字段。 |
| 关键设计 | 规则生成、单条 SELECT、Authorizer 白名单、单次修复、日志和评测。 |
| 验证结果 | 固定场景的成功率、拦截率、拒绝率均为 100%，但明确说明样本量。 |
| 限制与扩展 | 规则覆盖有限；接 LLM 前后安全层保持不变，后续加入 Schema Prompt、SQL Parser 和更大评测集。 |

## 高频追问

### 为什么当前先用规则，而不是直接接大模型？

规则能先把 SQL 查询的工程链路和安全边界验证清楚：什么问题允许回答、能访问哪些表字段、失败怎么处理、如何评测。当前支持范围小，但输出稳定、可解释。真实模型适合替换“问题到 SQL”的上游模块，不能替代权限控制和执行校验。

### 只做 SQL 字符串关键字拦截够不够？

不够。字符串检查可以拦截常见危险操作，但对嵌套查询、别名和数据库内部对象不够可靠。因此项目在实际执行连接上设置 SQLite Authorizer，让数据库读取表或字段时再做一次权限判断。这是“生成层不可信，执行层必须兜底”的设计。

### 为什么只允许 SELECT？

这个项目的业务目标是数据分析，而不是修改业务数据。对于自然语言驱动的系统，写操作会引入误操作和权限扩大风险。需要写数据时，应拆出独立工作流，加入身份认证、参数校验、人工审批和审计日志，而不是复用查询接口。

### 为什么只修复一次？

无限重试会放大延迟和资源消耗，还可能让错误 SQL 重复执行。项目只针对 `total_price`、`order_status`、`product_name` 等已知字段错误做一次确定性替换；第二次失败立即返回错误，方便定位和审计。

### 100% 指标是否说明项目已经可用于生产？

不是。100% 仅针对当前固定评测集：4 个正常问题、4 条危险 SQL，以及少量无效和失败案例。它证明当前边界下的回归测试通过，不能说明对任意自然语言、任意数据库或生产负载都有同等效果。我会扩充数据规模和测试集后再比较指标。

### 如果接入真实大模型，安全设计怎么变化？

模型只负责根据 Schema 和业务问题提出 SQL 草案。SQL 仍必须经过单语句检查、只读限制、表字段白名单、行数限制和数据库 Authorizer，再执行。模型输出失败时可以做一次受限修复，不能让模型直接获得数据库写权限。

## 现场演示顺序

1. 输入“各商品的销售额是多少？”，展示生成 SQL、表格、图表和解释。
2. 输入未知问题，展示系统拒绝而不是编造 SQL。
3. 运行危险 SQL 与权限测试，展示 DELETE、系统表和未授权字段被拒绝。
4. 运行修复测试，说明最多两次执行和停止条件。
5. 运行综合评测，展示固定用例与指标范围。

## 不应这样表述

- 不说“模型能自动查询任意业务数据”，当前不是。
- 不说“100% 准确”，应说“当前固定评测集通过率为 100%”。
- 不说“已经是生产级 Agent”，应说“已完成受控 SQL 查询原型的安全、评测和部署链路”。
