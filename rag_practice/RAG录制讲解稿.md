## 3 分钟讲解与操作

### 0:00 - 0:20 项目定位

屏幕：项目首页，暂不输入问题。

讲解：

> 这是我独立完成的 NEXUS RAG 求职知识库助手。它将岗位 JD、技术官方文档和面试笔记整理为 Markdown 知识库。当前页面展示 18 份文档和 35 个检索片段。用户提问后，系统先检索相关资料，再让模型基于证据生成回答，并在页面展示来源，避免把模型的自由生成当作事实。

### 0:20 - 1:20 真实模型问答

屏幕操作：在输入框输入 `怎样把项目上线？`，点击“检索并生成回答  ->”，等待回答出现。停留在 `GROUNDED RESPONSE`、`LLM | 基于检索证据生成` 和“引用来源”区域。

讲解：

> 这里我提问怎样把项目上线。后端会先将问题向量化，与知识库片段进行相似度检索，召回 Top 3 证据。然后把问题和证据一起发送给模型。页面的 `LLM | 基于检索证据生成` 状态说明本次实际使用了模型，而不是离线抽取式回退。
>
> 下方展示了 Docker 部署、Docker 官方文档和 FastAPI 官方文档等来源，以及每条来源的相似度。这样用户可以追溯答案依据，也便于我排查检索是否正确。

### 1:20 - 1:50 无依据拒答

屏幕操作：将问题改为 `公司年会什么时候举办？`，点击“检索并生成回答  ->”。停留在 `REFUSED | 当前资料不足` 和“未找到可引用的资料”。

讲解：

> 对于知识库中没有依据的问题，系统不会让模型编造答案，而是返回“根据现有资料无法确定”，并且不返回来源。这是通过相似度阈值控制的拒答分支，和真实模型生成分开处理。

### 1:50 - 2:30 评测和优化

屏幕操作：切换到 GitHub README 的“当前评测结果”与“失败案例复盘”章节，或本地打开 README。

讲解：

> 我为项目准备了固定评测集。当前知识库有 18 份文档、35 个片段，固定测试集的 Top 3 召回率和来源引用完整率都是 100%。我也保留了失败案例：相近文档会发生 Top 1 排序竞争，所以当前不能把 Top 1 指标包装成完美结果。
>
> 性能上，知识库扩充后，每次重新编码所有文档会让平均响应时间上升到 674 毫秒。我定位到重复计算文档向量的问题后，加入进程内缓存，将平均响应时间降到 253 毫秒左右。

### 2:30 - 3:00 收尾与边界

屏幕：README 的真实模型验收或 Docker 章节。

讲解：

> 项目通过 FastAPI 提供接口、Streamlit 提供演示页面，并完成了 Docker 健康检查。真实模型调用、离线回退和无依据拒答都有明确状态标识。当前限制是评测集规模较小、缓存只在单进程有效、尚未提供公网部署和多轮会话；下一步会扩充评测集，并增加文档上传和用户反馈能力。
